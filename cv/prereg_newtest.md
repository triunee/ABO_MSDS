# 새 test 평가 사전 등록 (초안)

- 작성 2026-11-06. **새 test 문서를 누구도 열기 전에** 커밋한다. 이 파일의 커밋 시각이 문서 선별 · 정답 작성 · 추론보다 앞선다는 것이 기준을 결과에 맞추지 않았다는 근거다.
- 대상은 CV 45건과 별개로 새로 받은 국문 MSDS다. 팀 과업의 test(31건, `report/test_manifest.csv`)와는 다른 세트이고, 그 봉인은 건드리지 않는다.
- 결과를 본 뒤에는 이 파일을 고치지 않는다. 바꿔야 하면 새 사전 등록을 만들고 이유를 적는다.
- 공개 저장소이므로 이 파일과 결과 파일에 새 test의 파일명 · 제조사 · 정답에서 나온 값을 적지 않는다. 자료 위치는 `<NEWTEST_ROOT>`(저장소 밖)로만 적는다.

## 1. 비교군 — 이미 있는 모델만 쓴다(새 학습 없음)

| 조건 | 모델 | 문서당 점수 |
|---|---|---|
| base_zs | Qwen3-4B(r1.yaml의 model_revision), zero-shot | 1회 |
| base_fs | 같은 베이스 + few-shot 2건(`eval/fewshot.json`, CV train 문서) | 1회 |
| r1 | CV fold 0~4 어댑터 5개(`cv/runs/r1/fold*/adapter`, seed 42) | 5개 모델 점수의 평균 |
| r1_aug | CV fold 0~4 어댑터 5개(`cv/runs/r1_aug/fold*/adapter`, seed 42) | 5개 모델 점수의 평균 |

- **왜 새로 학습하지 않나:** test를 본 뒤 학습 설정을 고를 여지를 없앤다. 어댑터는 이미 있고, 아래 해시로 지금 고정한다. 45건 전체로 다시 학습하면 val이 없어 학습 스크립트를 바꿔야 한다.

## 2. 문서 선별 — 규칙을 먼저 정하고 기계적으로 적용한다

선별은 개발 세션 밖에서 한다(3절). 개발 세션은 단계마다 **남은 건수와 제외 사유별 건수**만 받는다.

1. **국문 MSDS만** 남긴다.
2. **1~3항을 쓸 수 있어야 한다.** `core/`의 추출기로 1~3항 텍스트를 만들고, 실패는 `_cut_log.csv`에 남긴다. 다음은 뺀다(plan 6절과 같은 기준).
   - 추출 텍스트 200자 미만(스캔 PDF로 봄)
   - 2항 또는 3항 헤더가 없음
   - 4항 제목을 못 찾고, 수동 확인으로도 1~3항을 자를 수 없음
3. **학습에 쓴 제조사를 뺀다.** CV 45건의 제조사 그룹(`data/splits.csv`의 `split_group`, 관계사 포함)과 같은 제조사의 문서는 뺀다.
4. **노출 문서를 뺀다.** 파일럿 노출 문서 87건(파일럿 `data/sources.csv`)과 같은 문서(같은 제조사의 같은 제품)는 뺀다.
5. **중복은 하나만 남긴다.** 파일 내용이 같거나 같은 제품의 개정판이면 가장 최근 개정 1건만 남긴다.
6. **50건을 고른다.** 남은 문서를 PDF 파일 sha256 오름차순으로 세우고, 제조사 그룹당 최대 5건까지 앞에서부터 담아 50건을 채운다. 50건이 안 되면 남은 문서를 모두 쓴다. 사람이 문서를 골라 넣거나 빼지 않는다.

- 선별이 끝나면 문서마다 서식(`현행` · `수입품 국문판` · `구서식`, `data/splits.csv`의 `form`과 같은 기준)과 제조사 그룹을 정한다.
- 30건 미만이 남으면 그대로 평가하고, "방향 확인 규모"라고 문서 수 · 그룹 수와 함께 보고한다.

## 3. 정답 만들기 · 봉인 — 개발 세션 밖에서

- **어디서:** 정답 작업은 이 저장소에서 연 개발 세션과 다른 세션에서 한다. 자료는 모두 `<NEWTEST_ROOT>`(저장소 밖)에 둔다. 개발 세션에는 파일 · 목록 · 내용을 넣지 않는다.
- **규칙:** 지금 HEAD의 `docs/plan.md` 2절과 `data/README.md`를 그대로 따른다. 새 test를 보고 규칙을 고치지 않는다. 규칙에 없는 경우는 정답 작업 쪽 메모에만 남기고, 평가가 끝난 뒤 공개한다.
- **방법:**
  1. LLM이 1~3항 텍스트에서 스키마 JSON 초안을 만든다.
  2. 참고용 규제 DB가 있으면 초안과 대조해 **서로 다른 칸만 표시**한다. 규제 DB 값은 정답으로 쓰지 않는다. 정답은 원문에 적힌 값이다(plan 1절 설계 원칙).
  3. 사람이 원문 PDF와 모든 칸을 대조해 확정한다(100%).
  4. `python3 scripts/validate_labels.py <NEWTEST_ROOT>/labels`를 통과해야 한다.
- **봉인:** 정답 · 1~3항 텍스트 · 서식 목록 · 제조사 그룹 목록 4종의 해시를 `cv/newtest/test_manifest.csv`에 남긴다(`eval/seal.py`, 파일 이름 없음). 이 manifest를 커밋한 뒤에만 추론한다.

## 4. 판정 — 주지표 doc_exact_ext, 제조사 그룹 부트스트랩 95% 구간(10,000회, `eval/paired.py`와 같은 seed)

### 4-1. 주 판정: r1 vs base_fs (plan 10절의 질문)

문서마다 (r1 5개 모델 평균) − base_fs를 내고, 그 구간으로 결론을 고른다.

| 결과 | 결론 |
|---|---|
| 하한 > 0, 악화 필드 없음 | "학습에 쓰지 않은 제조사 {그룹 수}곳 {문서 수}건에서 학습의 이점이 확인됐다" |
| 구간이 0을 포함 | "few-shot과의 정확도 차이를 확인하지 못했다" — 동등하다는 뜻이 아니다. 입력 토큰 비율을 함께 적는다 |
| 상한 < 0 | "few-shot보다 정확도가 낮다" + 떨어진 필드, 입력 토큰 절감과의 교환 관계 |

- **악화 불허:** parse_rate · schema_rate · product_name_acc · cas · pair가 base_fs보다 낮으면 "이점이 확인됐다"고 쓰지 않는다.

### 4-2. 레시피 판정: r1_aug vs r1

- 문서마다 (r1_aug 5개 평균) − (r1 5개 평균). 하한 > 0이고, parse_rate · schema_rate · cas · pair가 r1보다 낮지 않을 때만 "새 문서에서 개선 확인"이라고 쓴다. 아니면 "새 문서에서 개선을 확인하지 못했다"라고 쓴다.
- 이 판정은 CV 판정(`cv/prereg_r1_aug.md`)과 따로 보고한다. 둘을 합쳐 하나의 성공으로 만들지 않는다. 한쪽만 통과하면 둘 다 그대로 적는다.

### 4-3. 참고로만 적는 것(판정에 쓰지 않음)

- base_zs 대비 짝 비교, 필드별 · 서식별 수치(합산하지 않음)
- 같은 조건 5개 모델 사이에서 결과가 갈린 문서 수(학습 데이터 차이로 생기는 흔들림)
- 문서당 입력 · 출력 토큰, 생성 시간, 추출 실패율(실패 건을 분모에서 빼지 않음)
- Rule Engine 탐지율(`eval/cv_rules.py`와 같은 방식)

## 5. 실행 환경

- 추론은 RunPod **RTX 4090 24GB** 한 종류에서 모든 비교군을 돈다. 패키지 버전은 `cv/prereg_r1_aug.md` 1.1절과 같다.
- 4090을 빌릴 수 없으면 **첫 추론을 시작하기 전에만** 다른 24GB급 GPU로 바꿀 수 있다. 바꾸면 이 줄을 고쳐 다시 커밋한다. 한 번 시작하면 비교군을 서로 다른 GPU 종류에서 섞어 돌리지 않는다.
- 어댑터는 노트북(RTX 4060 Laptop)에서 학습했다. 학습 GPU와 추론 GPU가 다르지만, 모든 비교군이 같은 조건이다.
- 비교군마다 1회만 추론한다. 다시 돌린 결과로 바꾸지 않는다(실패하면 원인을 적고, 같은 설정으로 끝난 문서만 이어서 돈다).
- 추론 수: 50건 × (base_zs 1 + base_fs 1 + r1 5 + r1_aug 5) = 600회. 4090에서 문서당 11~15초로 보면 약 1시간 50분~2시간 30분, 준비까지 약 2시간 20분~3시간이다(추정).
- 출력 · 채점 상세는 `<NEWTEST_ROOT>/out/`(저장소 밖)에만 둔다. 저장소에는 문서 이름 없는 집계(`cv/newtest/report.md` · `scores.csv` · `paired.csv`)만 커밋한다.

## 6. 평가 전에 구현할 것(test 자료 없이 fixture로만 검사)

1. `eval/seal.py` · `eval/infer.py` · `eval/score.py` · `eval/paired.py`에 `--manifest` 옵션. 기본값은 지금처럼 `report/test_manifest.csv`로 두어 팀 test 동작을 바꾸지 않는다.
2. 새 test 고정 파일 `cv/newtest/experiment.json`: max_new_tokens · 프롬프트 버전 · 1절 어댑터 해시 10개. 추론은 어댑터 해시가 이 목록에 없으면 거부한다.
3. 집계 `eval/newtest.py`: 어댑터별 채점 → 문서마다 5개 평균 → 4절 판정. `eval/cv.py`의 seed 평균 판정과 같은 부트스트랩을 쓴다.
4. 회귀 테스트: `test/`에 fixture로 위 1~3을 검사하는 테스트를 더한다.

이 구현은 정답 작업과 따로 진행할 수 있다. 판정 규칙(4절)은 이 파일이 기준이고, 코드는 이 규칙을 그대로 계산해야 한다.

## 7. 한계 (보고서에 그대로 밝힌다)

- 정답을 만드는 사람이 개발자 본인이다. 2차 검수자가 없다. 그래서 1 · 2 · 4절을 정답 작업보다 먼저 고정했다.
- 새 문서의 제조사 분포는 선별 전에는 모른다. 그룹 수가 적으면 구간 추정 자체가 불안정하다.
- r1 · r1_aug는 fold 어댑터의 평균이다. 하나의 최종 모델 점수가 아니다.
- seed는 42 하나다. CV에서 seed만 바꿔도 45건 중 8건이 뒤집혔다. 4-2의 결과는 이 잡음을 함께 감안해 읽는다.

## 8. 실행 순서

1. 이 파일을 커밋 · push한다(새 test 문서를 열기 전). 이 커밋 해시가 "새 test 사전 등록 커밋"이다.
2. 6절 구현을 커밋한다(개발 세션, test 자료 없음).
3. 정답 세션에서 2절 선별 → 3절 정답 · 봉인. manifest를 커밋한다.
4. RunPod에서 6절 도구로 비교군마다 1회 추론 → 채점 → `eval/newtest.py` 판정.
5. 집계 결과를 커밋하고, CV 결과와 섞지 않고 나란히 보고한다.
